## Verified problems (each: file:line or metric, what is wrong, concrete fix)
1. Decision optimum is a grid-edge artefact. `decision.py:25-26` sets `t_grid` upper bound to the 99th percentile of the RUL samples; `main.py:350` takes `t_star` from it. t* = 7.515 equals that edge, and fig9_decision.png shows J(t) still falling at the right end for every derate level. Fix: extend the grid (e.g. to max(RUL samples) times 2 or a fixed horizon), assert that argmin is interior and otherwise flag "no interior optimum", and print J at the optimum. The sensitivity result t*(c_f=2,5,10) = 7.515 for all three (details.json decision.t_star_by_cf) is the same symptom: the argmin is set by the RUL tail, not by the costs.
2. Decision contradicts the data it is supposed to act on. Case 1 cutoff tau = 36 (75% of life). Observed VB first reaches 0.45 at t = 41 (0.50 at t = 44), i.e. about 5 units after cutoff. The "optimal" replacement is at tau + 7.5 = 43.5, after the observed crossing, while the same stage has P(VB>0.45) = 0.625 and posterior median RUL = 0. Fix: after fixing item 1, require t* < posterior-median crossing or report the conflict explicitly. J is also labelled "per unit output" (`decision.py:10`, `main.py:395-397`) but its denominator is a time E[min(T,t)]; the brief asks for cost per unit time, so relabel or change the formula.
3. MCMC is not converged and the diagnostic is hidden. `metrics.json` calibration.mean_autocorr_time = 166.6 with 4500 post-burn steps gives chain/tau = 27, below the emcee threshold of 50. `uq_calibration.py:71` calls `get_autocorr_time(..., quiet=True)`, which suppresses emcee's "chain too short" warning. `main.py:48` uses N_STEPS = 6000, while BRIEF_COMMON asks for about 1500 steps. Fix: drop quiet=True, report per-parameter tau and chain/tau, and either lengthen or thin the chain or state "not converged" in the summary. Note that 3 of 5 posteriors are as wide as the prior (posterior-to-prior ratios 0.89, 0.68, 0.96, 1.02 for log10B, Ea_R, alpha, log10hA), i.e. prior-dominated.
4. Physics model has almost no force signal. The force proxy u(t) = smcDC is flat within each case (within-case CV 1-3% for 13 of 15 cases; raw CSV values), so the ODE reduces to VB ~ 10^log10A * qn * t * g(T). Sobol (`metrics.json` sobol) confirms this: log10A ST = 0.93, while log10B, alpha, log10hA have ST < 0.03 and Ea_R 0.14. The thermal constants (ETA = 5, T_inf = 300, DT_MAX = 400, `physics_model.py:26-28`) are fixed, so the "physics" is essentially a load-scaled time law. Fix: add an empirical baseline VB = a * qn^p * t^q (log-linear, fitted on training folds) to the held-out table and say whether the ODE beats it. Also fix or mask the entry transient in case 1 (runs 1-4, smcDC 0.13-0.67 against about 1.4 later; `data_loader.py` does not handle it), which currently enters u(t) by interpolation.
5. Grouped CV leaks replicate operating conditions. Readme Table 2 and the CSV show that the 16 cases are 8 settings x 2 insert sets: (1,9), (2,12), (3,11), (4,10), (5,16), (6,15), (7,13), (8,14) share DOC, feed and material. `surrogate_model.py` features include DOC/feed/material and `make_folds` (`data_loader.py:43-49`) splits by case, so each test case's twin is in the training set (fold 0 test = 1,7,12; their twins 9,13,2 are all in training). The DataDriven and Hybrid scores (`heldout_nrmse` 0.545 and 0.486) are therefore optimistic for unseen settings. Fix: GroupKFold over the 8 settings (4 folds of 2 settings) and report it next to the case-grouped result.
6. Emulator is weak in the regime that matters. `metrics.json` surrogate.rmse = 0.252 mm against VB_crit = 0.45 mm; R2 = 0.95 is dominated by the large-VB region. `surrogate_model.py:100-101` computes rmse_near_0p6 but it is not written to metrics.json or summary.md. `VB_CAP = 3.0` (`surrogate_model.py:20`) clips the emulator output, which changes Sobol variance and RUL crossings (the summary admits this but does not quantify it). Fix: report RMSE restricted to VB <= 0.6 mm and the crossing-time error for each calibration case; remove or justify the cap with a number.
7. Calibration coverage is explained incorrectly and the 25% result is uninformative. Per summary.md line 70, low coverage at 25%/50% is attributed to later points lying "far beyond the calibration window". `fig4_calibration_case1.png` (middle panel) shows case 1 at 50%: the held-out points lie 2-24 units after the cutoff and sit below a band that is above them throughout (0/8 covered, RUL median 1.3 vs observed bracket 14-17). That is systematic over-prediction (model bias), not extrapolation distance. The 25% stage has coverage 1.00 only because its 95% band runs from about -0.1 to 3.8 mm (left panel); it also goes negative, which an additive Gaussian noise model on a non-negative quantity allows. Fix: report interval width and signed bias per stage, use a non-negative noise model (e.g. on log VB), and state the pooled 0.74 against nominal 0.95 as under-coverage.
8. Results are stale relative to the code and the fit is not fully reported. results/metrics.json and summary.md are timestamped 12:06, while main.py and src/*.py are 12:08. The on-disk summary lacks the columns that the current `main.py:529` writes (later-point coverage, RMSE near 0.6 mm) and the MCMC verdict and decision caveat that the current code writes (`main.py:559-562`, `577-579`). Also details.json shows fold 0 physics fit used nfev = 150 (= max_nfev, `physics_model.py:80`, not converged), fits sit at bounds (log10hA = -2 in fold 0; Ea_R = 0.001 in fold 0 and 311.6 in fold 4), and the design box was narrowed "to the region the least-squares fits occupy" (summary limitation), which used results from all folds. Fix: re-run main.py once the builder has finished, regenerate summary.md and metrics.json from that run, flag non-convergence, and either fix the box from training folds only or disclose the effect.
